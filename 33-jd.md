### 1. Compare RLHF, RLAIF, DPO, IPO and KTO: principles, pipelines, trade-offs, and which you would pick for e-commerce.

**Source**: https://outcomeschool.com/blog/reinforcement-learning-from-human-feedback-rlhf and https://outcomeschool.com/blog/direct-preference-optimization-dpo

**Anchor answer**

Two axes separate them: **who labels** (human vs AI judge) and **whether a separate reward model exists** (online RL vs offline preference loss).

| Method | Signal | Pipeline | Main cost / failure |
| :--- | :--- | :--- | :--- |
| RLHF (PPO) | pairwise human preference → RM → PPO | 4 models in memory (policy, ref, RM, critic) | most expensive, unstable; RM is a hackable proxy |
| RLAIF | preference from a strong judge model | same as RLHF, labels are cheap | inherits judge's bias; needs spot-check calibration |
| DPO | pairwise preference, closed-form | policy + ref, single supervised-style loss | no exploration; needs fresh on-policy-ish pairs; can overfit to length |
| IPO | pairwise, hard-coded preference strength | same as DPO | prevents over-optimisation, converges slower, sensitive to label noise level |
| KTO | binary thumbs up/down (no pairs) | single label per sample | matches real product telemetry, needs a well-set loss-asymmetry prior |

For e-commerce I would ship **KTO on production feedback** (thumbs, return/no-return, complaint/no-complaint — these are unpaired by nature) and keep **DPO as the cheap first pass**. Full PPO only if I need exploration against a simulator, which retail rarely has.

The trap: offline methods are only as good as the pair distribution. If your DPO pairs come from one template, the model learns "template A good, B bad", not the policy you wanted.

**中文要点**：两条轴——谁打标（人/AI）、有没有独立 RM；电商真实信号是**不成对**的（点赞、退货、投诉），所以 KTO 最贴合，DPO 做廉价首选，PPO 只在有模拟器可探索时才值得。

### 2. How do you design the reward function for LLM RL, and how would you build a high-quality reward signal for product dialogue or recommendation?

**Source**: https://outcomeschool.com/blog/group-relative-policy-optimization-grpo

**Anchor answer**

Never one scalar. Decompose, then weight:

| Component | Shape | How measured |
| :--- | :--- | :--- |
| Task success | 0/1 | rule check on the final structured field (SKU, address, refund amount) |
| Factuality | graded penalty | NLI/claim check against the retrieved doc, not against the model's own output |
| Policy compliance | hard −∞ | deterministic validator (no coupon over cap, no out-of-stock promise) |
| Format | small bonus | schema parse success |
| Style | small, capped | length/verbosity **clipped**, or the model learns to pad |
| Business proxy | sparse | CTR/CVR/return-rate proxy from offline logs, heavily discounted |

Practical rules that only come from doing it:

1. **Put hard constraints in the mask, not the reward.** A reward penalty for "promised a discount that doesn't exist" gets traded off against task success; a logit mask or action filter does not.
2. **Clip every soft term.** Unclipped length or style rewards are the number-one reward-hack vector; the model finds the cheapest way to farm them.
3. **Normalise per group, not per batch.** GRPO's group-relative advantage already handles scale; a global normaliser makes easy prompts dominate.
4. **Audit the reward on frozen transcripts** before training: score 200 already-good and 200 already-bad outputs; if the separation is under ~1.5σ, the signal is noise and RL will amplify noise.

**中文要点**：别用单一标量——拆成任务成功/事实性/合规/格式/风格/业务代理六项；**硬约束放 mask 不放 reward**，软项全部截断，组内归一化，训练前先用冻结语料检验奖励的可分性。

### 3. How do you debug the usual instabilities in RL training of LLMs?

**Anchor answer**

Read five curves every N steps; each instability has a signature.

| Symptom | Underlying cause | First fix |
| :--- | :--- | :--- |
| Entropy collapses to ~0 early | advantage too sharp, LR too high, std-normalisation by tiny σ | raise temperature/entropy bonus, clip advantage, use group std floor |
| Reward up, KL explodes | policy drifting from ref faster than the RM can track | tighten KL target (adaptive β), lower LR |
| Reward flat, grad norm spiky | bad batches (all-correct or all-wrong groups → zero advantage) | drop degenerate groups, dynamic sampling |
| Length balloons | length correlated with reward in the RM | length-normalise or length-penalty; re-balance RM training data |
| Loss NaN | fp16 overflow in log-prob ratio; huge ratio after importance clipping | bf16, tighter ratio clip, grad clip 1.0 |
| Eval drops while train reward rises | reward hacking | held-out judge + human spot check, not the RM |

Order of debugging: **is the reward computed correctly on a fixed batch?** (offline replay), then **is the advantage distribution sane?**, then **is the sampler producing degenerate groups?**, only then hyperparameters. Nine out of ten "RL is unstable" reports are a data or advantage bug, not a PPO bug.

**中文要点**：看五条曲线——熵、KL、奖励、梯度范数、长度；八成"RL 不稳"其实是数据/优势估计 bug（全对全错的退化组、奖励算错），先离线复算 reward，再调超参。

### 4. Compare full fine-tuning, LoRA and QLoRA and justify your choice with what actually shipped.

**Source**: https://outcomeschool.com/blog/lora-low-rank-adaptation-of-llms and https://outcomeschool.com/blog/how-does-fine-tuning-work

**Anchor answer**

| | Full FT | LoRA | QLoRA |
| :--- | :--- | :--- | :--- |
| Trainable params | 100% | ~0.1–1% | ~0.1–1% on a 4-bit frozen base |
| Optimizer state | 2× params (Adam) | tiny | tiny |
| Memory driver | params + grads + states | base weights (fp16/bf16) | base weights at 4-bit NF4 |
| Quality ceiling | highest | close, drops on new-knowledge tasks | slightly below LoRA on hard reasoning |
| Merge | n/a | mergeable, zero inference cost | merge is lossy; usually keep adapter |
| Multi-tenant | one model per tenant | swap adapters per request | swap adapters, one base |

What actually ships in a retail setting: **LoRA on all linear layers at r=16–32, α=2r**, because a single base model plus per-scenario adapters (customer service, listing copy, review summary) is the only thing an ops team can operate. QLoRA when the GPU budget is one 24–48 GB card and the task is style/format adaptation, not new domain knowledge.

The trade-off nobody mentions up front: QLoRA's on-the-fly dequantisation costs roughly 20–40% step time, so "fits on one card" and "trains fast" are different questions. And if your eval set is 100 examples, you cannot tell LoRA from full FT — build the eval first.

**中文要点**：全参微调上限最高但运维不了；实际落地是 **LoRA 全线性层 r=16~32 + 一基座多 adapter**；QLoRA 省显存但反量化慢 20~40%，且只适合风格/格式适配，不适合灌新知识。

### 5. How does context window length affect performance, and how do you push past the window limit?

**Anchor answer**

Three separate effects, often conflated:

1. **Quality**: attention is U-shaped in position — head and tail are used, the middle decays ("lost in the middle"). Doubling the window does not double usable context; effective recall at 50% depth is measurably worse than at 5%.
2. **Cost/latency**: prefill is quadratic in prompt length; KV cache is linear in tokens × layers × heads. A 128k prompt can cost more than 30 short calls.
3. **Distraction**: more retrieved-but-irrelevant text lowers accuracy even when it fits. Precision beats recall inside the prompt.

Pushing past the limit, cheapest first:

| Technique | When it works | Cost |
| :--- | :--- | :--- |
| Retrieval / chunk-and-select | large corpus, narrow question | index build, recall risk |
| Hierarchical summarise-then-answer | long documents, overview questions | summary loss on details |
| Sliding window + state carry | streaming/log analysis | state design |
| RoPE scaling (NTK/YaRN) + short continued pretrain | genuinely need long native context | retraining, quality dip on short tasks |
| KV compression / sparse attention | serving many long sessions | infra complexity |

Choose retrieval first. Extended context is a *product* decision (cost per query), not a free upgrade.

**中文要点**：窗口变长有三件事——质量（中段衰减）、成本（prefill 二次方、KV 线性）、干扰（无关文本拉低准确率）；优先做检索分层，长上下文是成本决策而不是免费升级。

### 6. Which inference optimisation tools have you used (TensorRT, vLLM)? How do they work and what was the experience?

**Source**: https://outcomeschool.com/blog/how-does-vllm-work and https://outcomeschool.com/blog/how-does-tensorrt-llm-work

**Anchor answer**

| | vLLM | TensorRT-LLM |
| :--- | :--- | :--- |
| Core idea | PagedAttention (paged KV blocks) + continuous batching | ahead-of-time compiled engines, fused kernels, in-flight batching |
| Strength | fast to adopt, HF-compatible, flexible sampling | peak throughput/latency on a fixed shape and GPU |
| Weakness | less peak perf, Python scheduler overhead | build step per model/GPU/precision; recompile on any change |
| Ops reality | one image, many models | engine cache as an artifact, pinned CUDA/driver |

vLLM's real wins, in order: **continuous batching** (a finished sequence frees its slot immediately, so throughput holds under mixed lengths), **paged KV** (no 2× over-reservation from max-length allocation, so you fit more concurrent sessions), then prefix caching.

Things learned in production:

- **Prefix caching only pays off when prefixes are genuinely shared** — system prompt plus tool schema. If every request has a unique user preamble, the hit rate is near zero and you paid for hashing.
- **Quantised KV cache is the cheapest 2× concurrency** when quality budget allows; measure with your own eval, not perplexity.
- **TensorRT-LLM wins on fixed-shape batched offline jobs**; vLLM wins on long-tail traffic and model churn. Most teams end up with vLLM online, TensorRT-LLM for the batch pipeline.

**中文要点**：vLLM 赢在 PagedAttention + 连续批处理，落地快；TensorRT-LLM 赢在编译后峰值性能，但每个模型/GPU/精度都要重新 build；前缀缓存只在 system prompt 真共享时才有效。

### 7. How do you handle hundreds of millions of records: cleaning, preprocessing, efficient loading, and the traps you hit?

**Anchor answer**

Treat it as a data pipeline problem, not a modelling one.

| Stage | Approach | Trap |
| :--- | :--- | :--- |
| Ingest | columnar (Parquet) + partition by date/tenant, never raw JSONL | small files kill throughput more than size does |
| Clean | rule filters first (length, language, boilerplate hash, PII regex), model filters second | filtering with a model costs 100× and is non-deterministic — version the filter |
| Dedupe | MinHash/LSH for near-dup, exact hash for dup | dedupe order changes the dataset; record it |
| Tokenise | offline, cache tokens, pack to fixed length | tokeniser is CPU-bound — it becomes the bottleneck long before IO is |
| Load | streaming shards, prefetch, deterministic shuffle by seed | shuffling the whole array of 100M indices needs GBs; shuffle shard order then within |
| Balance | sample by domain/length bucket | a random split leaks the same product into train and eval |

Actual numbers from retail-scale pipelines: 100M short documents is on the order of 10¹¹ tokens — the tokenised artifact is measured in **terabytes**, so "preprocess once, cache forever" is mandatory; re-tokenising per experiment wastes days. And always keep a raw immutable layer: when the cleaning rule is wrong, you must be able to re-derive without re-crawling.

**中文要点**：当成数据工程——Parquet 分区、规则过滤先于模型过滤、MinHash 去重并记录顺序、离线 tokenize 缓存（CPU 先成瓶颈）、分片内 shuffle；原始层不可变，清洗规则变了能重算。

### 8. A model degrades in production, worse quality or higher latency. Walk me through the full diagnosis.

**Anchor answer**

Split the two symptoms before touching the model — they usually have different causes.

**Latency** — decompose, don't average:

| Segment | What to check |
| :--- | :--- |
| Queue | concurrency vs capacity, KV-cache pressure, batch full |
| Prefill | prompt length grew? retrieval injected more chunks? |
| Decode | output length drift, sampling params changed |
| Post | reranker, tool calls, network |

**Quality** — order of likelihood:

1. **Input distribution shifted** (new products, new campaigns, new user segment) — check input length/embedding drift, not just logs.
2. **Dependency changed** — retrieval index rebuilt with a new embedding model, prompt template edited, model version silently bumped by the vendor. Diff the *effective* prompt, not the repo's.
3. **Feedback loop** — the model now recommends what it previously recommended; measure catalogue coverage, not accuracy alone.
4. **Model** — last on the list; base models rarely degrade without a deploy.

Method: replay a fixed golden set through production config weekly so you have a flat baseline; then bisect by shadowing traffic against the previous config. Without a replay harness every incident turns into archaeology.

**中文要点**：先拆开两个症状——延迟按队列/prefill/decode/后处理分解，质量按"输入漂移 → 依赖变更（索引、模板、模型版本）→ 反馈闭环 → 模型本身"排序；关键是每周用固定 golden set 回放生产配置。

### 9. Why do you need a reranker, and when can you skip it?

**Source**: https://outcomeschool.com/blog/how-does-a-reranker-work

**Anchor answer**

First stage maximises **recall cheaply** (bi-encoder / BM25, O(1) per doc via precomputed vectors), second stage maximises **precision expensively** (cross-encoder scores query+doc jointly, no precomputation).

Why the gap exists: a bi-encoder compresses a document into one vector *before knowing the query* — that is the price of precomputation, and it loses negation, numbers, and rare-entity matching. A cross-encoder reads both together and typically lifts nDCG@10 by a wide margin on the same candidate set.

When to skip it:

- Candidate set is already tiny (≤20) and mostly exact matches — e.g. SKU lookup by ID.
- Latency budget is under ~100 ms end-to-end and the reranker is the only thing that doesn't fit.
- The task is "find the one exact document" and BM25 already ranks it first; a reranker can only make it worse by moving a perfect result down.
- You have no labelled queries — then tune with a synthetic set first, or you are optimising blind.

Production shape: retrieve 100 → rerank 50 with a small cross-encoder → keep 5–8 for the prompt. Batch the reranker, cache by `(query, doc_id)`, and timeout it with fallback to the first-stage order.

**中文要点**：双塔为了可预计算把文档压成一个向量，天然丢否定/数字/罕见实体；交叉编码器联合打分补精度。候选集很小、延迟预算紧、或没有标注数据时可跳过；线上做 100→rerank 50→留 5~8。

### 10. How do you evaluate recall and precision for hybrid retrieval, and should RRF's k be larger or smaller?

**Source**: https://outcomeschool.com/blog/how-does-hybrid-search-work

**Anchor answer**

**Evaluate per retriever and per stage**, never on the fused output alone:

| Metric | Where | Why |
| :--- | :--- | :--- |
| Recall@k (k=20/50/100) | each first stage | the ceiling the reranker can reach |
| MRR / nDCG@10 | fused, then reranked | ranking quality, not just presence |
| Precision@5 | after rerank | what actually enters the prompt |
| Coverage / zero-result rate | production logs | unlabelled proxy that catches gaps |

Build the labelled set from real queries with graded relevance (0/1/2), 300–500 queries is enough to see differences; stratify by query type (SKU code vs natural language vs long tail), because hybrid helps long-tail semantic queries and can *hurt* exact-ID queries.

**RRF k**: score = Σ 1/(k + rank). Smaller k → the top few ranks dominate (sharp, brittle, close to "winner takes all"); larger k → the curve flattens and deeper ranks contribute (smoother, more robust to one retriever being wrong). The commonly cited k=60 is a smoothing default for many lists; if you only fuse two lists of 50, **k in the 10–30 range often ranks better** because ranks 1–5 still carry signal. Tune it on your labelled set — it is one cheap hyperparameter and it changes nDCG@10 materially.

**中文要点**：分阶段评——各通道 Recall@k（上界）、融合后 nDCG/MRR、rerank 后 P@5、线上零结果率；RRF 的 k 越小越尖（重头部），越大越平滑；只融合两路时 10~30 常优于 60，必须用标注集调。

### 11. Using Elasticsearch as a vector store, how do you combine vector and keyword retrieval, and how do you shard RAG?

**Anchor answer**

Combination, in order of preference:

1. **Native hybrid in one query** — `dense_vector` kNN + `match` in a `bool/should`, fused with RRF (`rank_constant`) or a weighted linear blend. One round trip, one filter context.
2. **Two queries + client-side RRF** — more control, more latency, needed when the two indexes have different filters.

Key ES specifics people get wrong:

- `knn` with a filter is **post-filtered inside HNSW**: `num_candidates` must be much larger than `k` or recall silently collapses. Set `num_candidates ≈ 10 × k` and measure.
- Vector dim and `similarity` are fixed at mapping time; changing the embedding model means a **new field + reindex**, so plan a versioned index alias from day one (`products_v3` behind `products_read`).
- Keyword side needs the right analyser: Chinese product titles need an IK-style tokeniser plus a synonym/alias dict, otherwise BM25 recall is poor and hybrid just inherits it.

Sharding: shard by **tenant or category**, not by hash, if half your queries carry a category filter — routing avoids scatter-gather. Keep shard size in the 10–50 GB range, and separate hot (recent, small) from cold (archive) indices so the working set stays in page cache. For RAG specifically, keep chunk text and vectors in the same doc so a hit needs no second fetch.

**中文要点**：优先用 ES 原生 hybrid 一次查询做 RRF 融合；注意 knn 的 filter 是后置过滤，`num_candidates` 要给到 10×k 否则召回静默崩塌；embedding 换模型必须新建字段+别名切换；分片按租户/类目路由而非哈希。

### 12. Design the degradation strategy for a RAG service. What triggers it?

**Anchor answer**

Degradation is a **ladder of increasingly lossy answers**, not a single fallback.

| Trigger (measured) | Detect by | Fallback |
| :--- | :--- | :--- |
| Reranker p99 over budget | per-stage latency histogram | skip rerank, use first-stage order |
| Retrieval returns nothing / low score | max score below threshold, empty set | BM25 only; then "no answer + ask user to refine" |
| Vector store down / shard unassigned | health probe, error rate | keyword-only index (separate cluster) |
| LLM 429/timeout | error budget burn rate | smaller model or shorter context, then static FAQ |
| Judge/eval score drop on live sample | canary scoring of 1% traffic | pin previous prompt/index version |
| Context oversize | token count > limit | summarise chunks, keep top 3 |

Rules that matter more than the ladder:

1. **Never silently degrade.** Attach a `degraded: true` flag and the reason to the response and the trace; a wrong answer that looks normal is worse than a slow one.
2. **Trigger on user-visible symptoms, not internal ones** — p95 latency and empty-result rate, not "CPU is high".
3. **Fail closed on high-stakes intents** (refund amounts, legal): say "can't answer now, here's a human", never guess.
4. **Rehearse it** — a monthly game day that kills the reranker and the vector shard; untested fallbacks do not exist.

**中文要点**：降级是阶梯（跳 rerank → 只留 BM25 → 换小模型/缩上下文 → 静态兜底 → 转人工），不是单一 fallback；每次必须带 `degraded` 标记进 trace，高危意图要 fail-closed，且每月演练。

### 13. Which database do you use for agent memory, and why?

**Source**: https://outcomeschool.com/blog/ai-agent-memory

**Anchor answer**

Match the store to the memory type — one database for all three is how projects stall.

| Memory | Content | Store | Why |
| :--- | :--- | :--- | :--- |
| Working (turn context) | messages, tool results | in-process + Redis (session TTL) | sub-ms, ephemeral, needs atomic append |
| Episodic | past task runs, outcomes | Postgres (+JSONB), or object store for big blobs | needs relational queries, audit, joins with user/business data |
| Semantic | facts, preferences, doc chunks | Postgres+pgvector or a dedicated vector DB | ANN search alongside metadata filters |
| Procedural | tool playbooks, skills | git-versioned files / prompt registry | must be diffable and reviewable |

Why I default to **Postgres with pgvector**: agent memory is 90% metadata queries ("this user's preferences from the last 30 days, still valid"), and vector search is only one predicate. One store means one transaction and one backup; a separate vector DB adds a consistency problem — you delete a memory in Postgres and the embedding lingers.

Redis is for the hot working set only; never the system of record, because eviction is a feature there. And every memory write needs **provenance (which turn produced it), a confidence, and a TTL** — otherwise the agent accumulates stale "facts" and confidently repeats them six weeks later.

**中文要点**：按记忆类型分库——工作记忆 Redis（TTL）、情节记忆 Postgres/JSONB、语义记忆 Postgres+pgvector（元数据过滤为主）、程序记忆用可 diff 的文件；默认 pgvector 是为了一个事务一份备份；每条记忆必须带来源、置信度和 TTL。

### 14. How does function calling work, and how does the model know which tool to call?

**Source**: https://outcomeschool.com/blog/how-does-function-calling-work-in-llms

**Anchor answer**

Mechanically: tool definitions are serialised into the prompt (name, description, JSON-Schema parameters), the model emits a structured call object, **the client executes it**, and the result is appended as a new message. Three layers make it reliable:

1. **Description quality** is the real API design — "search products by keyword, returns top 10 with price" beats "search". Ambiguity between two tools is the top cause of wrong calls.
2. **Constrained decoding** guarantees syntactic validity (grammar/JSON schema), not semantic correctness. A perfectly valid call can still name the wrong tool.
3. **Selection** is next-token probability over the serialised schema, so ordering and naming matter: tools with overlapping names compete in the same distribution. Few-shot examples of `(query → tool)` pairs move accuracy far more than longer descriptions.

Failure modes to expect: wrong tool among similar tools, right tool with missing required arg (the model "forgets" a field when the schema has many), nested-object args flattened incorrectly, and argument hallucination (an ID that looks plausible but doesn't exist). Mitigations: validate and return a typed error so the model can retry, keep the tool count per turn small (10–20), and always re-verify side-effecting arguments against the database before executing.

**中文要点**：工具定义序列化进 prompt，模型输出调用意图、客户端执行；语法由约束解码保证，语义（选对工具）靠描述+示例。高频失败是相似工具误选、必填参数漏填、ID 幻觉——小工具集 + 校验后把错误回灌。

### 15. How do MCP and Skills differ, and how do you think about prompts, MCP, skills and subagents?

**Source**: https://outcomeschool.com/blog/what-is-mcp-model-context-protocol

**Anchor answer**

They live at different layers and are not substitutes.

| Layer | What it is | Answers |
| :--- | :--- | :--- |
| Prompt | text in the request | "what should the model do right now" |
| MCP | a **protocol** (JSON-RPC) exposing tools/resources/prompts from a server | "how does the model reach an external system" |
| Skill | a **packaged procedure**: instructions + scripts + assets loaded on demand | "how do we do this task the way we've learned to" |
| Subagent | a separate context and loop with its own tools | "who does the long/isolated part" |

MCP solves **N×M integration** (N clients, M systems) and standardises discovery/auth/transport; a Skill solves **know-how reuse** and context economy — a 2k-token procedure only enters context when relevant. A skill may call MCP tools; an MCP server knows nothing about your procedure.

Composition rule of thumb: put *invariants* in the prompt, *capabilities* behind MCP, *multi-step know-how* in skills, and hand off when a subtask would pollute the main context (long search, big file analysis) to a subagent.

Anti-pattern: encoding business logic in a giant prompt because "it's easier than a tool". It cannot be tested, versioned, or permissioned, and it silently rots.

**中文要点**：四层不同——prompt 管当下指令、MCP 是接外部系统的协议（解 N×M）、skill 是可复用的流程包（按需加载省 context）、subagent 是独立上下文与循环；别把业务逻辑塞进巨型 prompt，它没法测、没法版本化、没法授权。

### 16. How do you constrain agent permissions to avoid unauthorised actions, especially around money?

**Anchor answer**

Assume the model will be wrong; make wrongness harmless.

| Control | Mechanism | Applies to |
| :--- | :--- | :--- |
| Capability scoping | each tool call carries a scoped token (user, tenant, max amount, expiry) issued by the runtime, not the model | all side effects |
| Two-phase execution | `prepare` returns a signed intent; `commit` requires a separate approval or a policy check | refunds, coupons, transfers |
| Hard limits | per-call and per-session caps enforced in code, plus a rolling daily budget | money |
| Allowlist | enum-constrained arguments (no free-form account IDs) | recipients |
| Sandbox | read-only DB replica, no prod credentials in the agent's env | exploration |
| Audit | every call logged with actor=agent, intent, approver, before/after diff | retrospection |
| Idempotency | key on (intent, args) so retries can't double-spend | money |

The core principle is **the model proposes, the platform disposes**: authorisation lives outside the model, in code the model cannot edit or argue with. Never encode limits in the system prompt — prompt injection or a long conversation can talk it out of them.

Practical: make irreversible actions a different tool from reversible ones, so the guardrail attaches to tool identity rather than to argument inspection.

**中文要点**：模型提议、平台裁决——权限用运行时签发的能力令牌、两阶段 prepare/commit、代码里的硬限额、枚举白名单、幂等键；绝不把限额写进 system prompt，可逆与不可逆动作要拆成两个工具。

### 17. What do you do when multiple agents disagree or play conflicting roles?

**Anchor answer**

Disagreement is information; unbounded debate is a bug. Pick an arbitration mechanism up front.

| Mechanism | Use when | Failure |
| :--- | :--- | :--- |
| **Domain ownership** — the agent that owns the data decides | clear responsibility split (inventory vs pricing) | boundary cases stall |
| **Judge agent** with the evidence, not the conclusions | open-ended analysis | judge inherits same blind spot if same model+context |
| **Vote over independent samples** | classification with cheap verification | correlated errors → confident wrong majority |
| **Escalate to human** | high-stakes, or confidence below threshold after 2 rounds | latency, cost |
| **Deterministic merge** (union of constraints) | plan composition | over-constrained, no feasible plan |

Rules I have learned:

1. **Cap rounds (2–3) and require new evidence each round.** Two agents re-arguing from the same context converge on whoever writes last — sycophancy, not consensus.
2. **Make disagreement explicit in the output** — "pricing says ¥99, inventory says unavailable" is far more useful than a smoothed answer. Silent averaging of contradictions is the worst outcome.
3. **Different roles need different contexts and different tools**, otherwise the "conflict" is one model talking to itself.
4. Give the judge the **raw tool outputs**, not the other agents' prose, or it just grades writing quality.

**中文要点**：先定仲裁机制——领域归属、裁判 agent（看原始证据不看结论）、投票、升级人工、约束合并；必须限制轮数且每轮要新证据，否则变成"谁说最后一句听谁的"；矛盾要显式暴露，不能悄悄平均掉。

### 18. Why Spring AI over LangChain4j, and how do you adapt agent frameworks on the Java side?

**Anchor answer**

| | Spring AI | LangChain4j |
| :--- | :--- | :--- |
| Idiom | Spring Boot starters, auto-config, `@Bean` model clients | standalone library, builder API, works without a container |
| Ecosystem fit | Micrometer, Actuator, Spring Security, `RestClient` | self-contained; lighter for non-Spring services |
| Advisors / interceptors | `CallAdvisor`/`AdvisorChain` around the model call | `AiServices` + memory/retriever wiring |
| Vector store | broad Spring-style abstraction layer | also broad, often simpler to configure |
| Tool calling | `@Tool` methods, schema from reflection | `@Tool` too; both rely on annotation scanning |

Choose **Spring AI** when the surrounding service is already Spring: you inherit configuration, observability, security context propagation and connection pooling for free, and the platform team only has to review one dependency model. Choose **LangChain4j** for a library-shaped component or a non-Spring runtime.

Adaptation strategy, the part that actually matters: define your **own thin port** (`LlmClient`, `ToolRegistry`, `MemoryStore`) and put the framework behind it. Frameworks churn fastest at the edges; the port keeps the business code stable and lets you migrate in one file.

Java-specific traps: blocking HTTP clients in a virtual-thread world need explicit timeouts; streaming via `Flux` must be back-pressured or a slow consumer holds the upstream connection; and tool execution inside a request thread can exhaust the pool — run long tools on a bounded executor.

**中文要点**：Spring 体系里选 Spring AI（白拿配置/观测/安全上下文），库形态或非 Spring 运行时选 LangChain4j；关键是**自己定义 LlmClient/ToolRegistry 薄端口**把框架挡在外面；Java 侧注意流式背压、超时、工具线程池隔离。

### 19. Why build a unified LLM service layer instead of calling model APIs directly?

**Source**: https://outcomeschool.com/blog/llm-routing

**Anchor answer**

Because every team calling a vendor directly duplicates the same ten concerns, badly and inconsistently.

| Concern | Without a layer | With a layer |
| :--- | :--- | :--- |
| Keys & quota | keys spread across services, leaked in repos | single egress, per-team quota |
| Cost | no per-feature attribution | token accounting by app/tenant |
| Failover | hard-coded single vendor | routing + fallback on 429/5xx |
| Compliance | PII leaving through unknown paths | redaction, prompt/response logging policy |
| Caching | nothing shared | semantic + prefix cache across apps |
| Versioning | silent model bumps break prompts | pinned model versions, recorded per request |
| Eval | no common harness | replayable traces, shared golden sets |

The layer should be **thin and boring**: auth, quota, routing, retries, logging/tracing, PII guard, cache. Resist making it a prompt framework — prompt logic belongs to the product team, otherwise every experiment needs a platform release.

Routing policy that pays: small model for classification/extraction, large only for open-ended generation, with a rule-based pre-classifier; add a quality gate that escalates on low confidence. Track cost per successful task, not per token — that is the number that survives a review.

**中文要点**：统一层只为收敛重复关注点——密钥与配额、成本归属、失败切换、合规脱敏、缓存、版本固定、trace 回放；保持薄，别把 prompt 逻辑塞进去；路由用"小模型做分类/抽取、大模型做生成"，并按每成功任务计成本。

### 20. Design an alerting agent: inputs, outputs, how you stay accurate during holidays and release windows, and the non-AI fallback.

**Anchor answer**

**Inputs**: metrics time series, log clusters (not raw lines), trace latency histograms, deploy/change events, calendar (promotions, holidays), and past incident records with resolutions.

**Outputs**: a ranked alert with `severity`, `affected_service`, `evidence` (top-k anomalous series with timestamps), `suspected_cause`, `suggested_runbook`, and `confidence`. Never a bare "something is wrong".

Accuracy across holidays and releases — the hard part:

| Problem | Mechanism |
| :--- | :--- |
| Seasonality breaks thresholds | compare against **same-weekday-same-hour baseline** and a seasonal model, not a global mean |
| Release windows cause known-noise | ingest change events; suppress or downgrade alerts attributable to an in-flight deploy, but **still log them** |
| Promotions change traffic shape | feature-flag calendar events; switch to "traffic-normalised" ratios (error rate per request) instead of absolute counts |
| Novel incidents | anomaly detection plus rule coverage; escalate unexplained-but-severe to human |

**Non-AI fallback**: static thresholds plus SLO burn-rate alerts on the critical path, always on, independent of the agent. The agent *augments* paging — it must never be the only thing watching. Route agent alerts through the same on-call pipeline, marked as `agent-suggested`, and measure precision weekly; if precision drops below the static rules, auto-demote to digest-only.

**中文要点**：输入指标/日志簇/trace/变更事件/日历/历史工单，输出带证据与置信度的分级告警；节假日用同星期同时刻基线，发布窗口按变更事件降级但不丢弃；静态阈值+SLO 燃烧率兜底，agent 精度跌破人工规则就自动降级为摘要。

### 21. Design incremental updates for a RAG system over thousands of pages and gigabytes of multimodal documents.

**Anchor answer**

The unit of work is a **chunk**, and the hard problem is identity, not throughput.

| Stage | Design |
| :--- | :--- |
| Detect | content hash per page + per chunk; store `doc_id, chunk_id, hash, embed_model_version` |
| Diff | chunk-level set difference against the previous version, not whole-document re-embed |
| Parse | layout-aware parser; cache the parse artifact per file hash (parsing is often the slowest step) |
| Embed | batch, cache by content hash — identical boilerplate across documents is extremely common |
| Apply | write new chunks, tombstone deleted ones, then swap an index **alias** (blue/green) |
| Verify | eval set replay before alias switch; compare recall on a fixed query set |

Traps:

1. **Chunk-boundary churn** — a one-line edit near the top shifts every downstream chunk, so the diff is 100% instead of 1%. Fix with stable anchors (heading path + offset) or content-defined chunking.
2. **Re-embedding is the cost centre**, not storage. Budget it, and never re-embed because the embedder version changed without a full blue/green rebuild.
3. **Multimodal**: images need captions or a vision embedder, and a table is not text — keep the table as structured data plus a text rendering, or numeric questions break.
4. **Deletes** must be first-class; stale chunks are the most common RAG correctness bug after a migration.

**中文要点**：以 chunk 为单位做内容哈希 diff，缓存解析产物与按哈希复用的 embedding；写新+墓碑删+别名蓝绿切换；最大坑是**分块边界漂移**导致全量重算、以及删除没做成一等公民留下陈旧块。

### 22. Design an AI development platform spanning training, evaluation, deployment and serving. How do you layer it?

**Anchor answer**

Layer by **who owns the interface**, so each team can move without blocking the others.

| Layer | Provides | Owned by |
| :--- | :--- | :--- |
| Resource | GPU pools, quotas, scheduling, storage volumes | infra |
| Data | dataset versioning, lineage, labelling, PII policy | data |
| Training | job templates (SFT/LoRA/RL), hyperparameter sweeps, checkpoint registry | ML platform |
| Evaluation | golden sets, judge models, regression gates, human review queue | ML platform + product |
| Artifact | model registry: weights, adapter, tokenizer, prompt template, eval report — **one immutable bundle** | ML platform |
| Serving | autoscaled inference, routing, canary, KV-cache pools, rate limits | infra/SRE |
| Observability | traces, token/cost accounting, online eval sampling | SRE + ML |
| Governance | approval flow, audit, access control, data residency | security |

The single most important design decision: **the deployable unit is the bundle** (weights + tokenizer + prompt + retrieval config + eval report), versioned together. If prompt and weights version independently, "which config produced this answer" becomes unanswerable, and every incident costs days.

Second: **eval is a gate, not a dashboard** — promotion requires passing on the golden set plus a canary on live traffic. Third: keep the platform boring at the top and pluggable at the bottom (support vLLM, TensorRT-LLM, and external APIs behind one interface) so a vendor change isn't a platform rewrite.

**中文要点**：按"谁负责接口"分层（资源/数据/训练/评测/制品/服务/观测/治理）；最关键决策是**可部署单元=一个不可变 bundle**（权重+tokenizer+prompt+检索配置+评测报告），否则事故无法归因；评测要是门禁而不是看板。

### 23. Level-order traversal of a binary tree.

**Reference implementation**

```python
from collections import deque


def level_order(root):
    if root is None:
        return []
    out, q = [], deque([root])
    while q:
        level = []
        for _ in range(len(q)):          # snapshot the level size
            node = q.popleft()
            level.append(node.val)
            if node.left:
                q.append(node.left)
            if node.right:
                q.append(node.right)
        out.append(level)
    return out
```

**Key points**

- `len(q)` snapshot **before** the inner loop is what separates levels; appending while iterating without it flattens the tree.
- Two-queue variant is equivalent but doubles memory; the size-snapshot version is one queue.
- Zigzag variant: keep a `left_to_right` flag and `level.reverse()` or `appendleft`, O(n) either way.
- Complexity O(n) time, O(w) space where w = max width — for a complete tree that is n/2, so it is not O(log n) like DFS.
- Iterative beats recursion here: a degenerate tree would blow Python's recursion limit at ~1000 depth.

**中文要点**：进入内层循环前先取 `len(q)` 才是分层的关键；用单队列+快照即可，空间是最大宽度 O(w) 而非树高；退化树用递归会爆栈。

### 24. Implement an LRU cache.

**Reference implementation**

```python
from collections import OrderedDict


class LRUCache:
    def __init__(self, capacity: int):
        if capacity <= 0:
            raise ValueError("capacity must be positive")
        self.cap = capacity
        self.d = OrderedDict()

    def get(self, key):
        if key not in self.d:
            return -1
        self.d.move_to_end(key)          # mark as most recently used
        return self.d[key]

    def put(self, key, value):
        if key in self.d:
            self.d.move_to_end(key)
        self.d[key] = value
        if len(self.d) > self.cap:
            self.d.popitem(last=False)   # evict least recently used
```

**Key points**

- `OrderedDict` gives O(1) amortised `move_to_end`/`popitem`; the interview answer is hash map + doubly linked list, and this is that, correctly implemented.
- `get` must also update recency — the classic bug is updating only on `put`.
- `put` of an existing key must not double-count capacity.
- Not thread-safe: under concurrency you need a lock, which serialises everything; shard the cache (e.g. 16 locks by hash) instead.
- For an LLM gateway, LRU on `(prompt_hash, params)` wastes memory on one-hit entries — use LRU+TTL or admission by second-hit (TinyLFU) instead.

**中文要点**：`OrderedDict` 即哈希表+双向链表，get 也要更新热度（经典 bug 只在 put 更新）；非线程安全，并发要分片加锁；LLM 网关上纯 LRU 会被一次性请求污染，宜 LRU+TTL 或二次命中才入缓存。

### 25. How do you handle high concurrency when deploying an LLM, and which tools do you reach for?

**Anchor answer**

LLM concurrency is not request concurrency — it is **KV-cache occupancy and token throughput**, and the two need different controls.

| Layer | Control | Tool |
| :--- | :--- | :--- |
| Edge | rate limit per user/tenant, token bucket, request size cap | Envoy/Nginx, Redis + Lua (atomic) |
| Admission | queue with bounded wait, shed load above capacity | in-process semaphore, queue-depth-based HPA |
| Batching | continuous batching, max batch tokens (not max sequences) | vLLM/SGLang scheduler |
| Cache | prefix cache for shared system prompts, semantic cache for FAQ | vLLM prefix caching, Redis |
| Timeout | TTFT timeout separate from total timeout, streaming heartbeats | gateway + client |
| Fallback | smaller model, shorter max_tokens, canned answer | LLM router |

Lessons from operating this:

1. **Autoscale on queue depth and TTFT, not CPU.** GPU util sits at 95% in every state; it tells you nothing.
2. **Max-tokens is the real capacity knob.** One request with `max_tokens=8000` can hold KV blocks for minutes; cap it and let callers opt in explicitly.
3. **Semantic cache has a correctness cost** — for personalised answers it serves the wrong user's answer. Scope it by tenant and only for stateless FAQ intents.
4. **Backpressure must reach the client** as a 429 with a retry hint; queueing silently inside the gateway converts overload into timeouts everywhere.

**中文要点**：LLM 并发本质是 KV 占用与 token 吞吐，不是请求数；按边限流（Redis+Lua）→ 准入队列 → 连续批处理（按 max batch tokens）→ 前缀/语义缓存 → TTFT 独立超时 → 降级；HPA 看队列深度和 TTFT，别盯 GPU 利用率。

### 26. How do you connect LLMs to your business surface (recommendation, retrieval, semantic understanding), and what was genuinely novel in your work?

**Anchor answer**

Three integration shapes, different risk profiles:

| Surface | LLM role | Success metric | Failure mode |
| :--- | :--- | :--- | :--- |
| Semantic understanding | query rewrite, intent/attribute extraction, title normalisation | downstream recall/CTR, extraction F1 | confident wrong attribute poisons retrieval |
| Retrieval | query expansion, reranking, chunk selection | nDCG, answer groundedness | latency, cost per query |
| Recommendation | explanation generation, cold-start item profiling, review summarisation | CTR/CVR, return rate | fluent explanations that don't match the reason |

What is genuinely novel is rarely the model call — it is usually the **interface between a probabilistic component and a deterministic pipeline**: caching extracted attributes so the LLM is not on the hot path, defining a schema the downstream ranker can consume, and having a rule-based fallback when confidence is low.

A concrete pattern worth describing: run the LLM **offline** to enrich the item/query corpus (attributes, summaries, embeddings), then at serving time only do cheap lookups and a rerank. That converts an unpredictable 300 ms model call into a bounded index read, which is what actually made the metric move. Online-only LLM calls in the ranking path are usually too slow and too variable for a revenue-critical surface.

**中文要点**：三种接法——语义理解（抽取/改写）、检索（扩召回/重排）、推荐（解释/冷启/摘要）；真正新颖的通常是"概率组件与确定性管线的接口"：离线用 LLM 富化语料、线上只做查表+重排，把不可控的 300ms 变成有界的索引读。

### 27. Walk me through a postmortem where online results missed expectations. How did you locate the cause?

**Anchor answer**

A structure that survives review:

1. **Restate the expectation and the measurement.** Which metric, which window, which population. Half of "missed expectations" postmortems end here — the offline estimate and the online metric were not the same quantity.
2. **Rule out instrumentation first.** Logging coverage, exposure bias (only users who saw the new widget), metric definition drift, and traffic mix shift. Cheap, and it is the cause maybe 20% of the time.
3. **Segment.** By user cohort, device, query type, category. Aggregate gains hiding segment losses is the classic: overall +1.2% CTR with the new-user segment at −6%.
4. **Check the coupling.** Offline eval measured a proxy (e.g. rerank nDCG) while the online goal was revenue; a better ranker can raise nDCG and lower GMV if it surfaces cheap items.
5. **Check the counterfactual.** Was the control actually the old system, or a slightly different old system? Position bias, novelty effect, and holiday traffic all inflate early results — look at the decay curve over two weeks.

The honest conclusion is often "the offline metric was the wrong objective", and the fix is a better offline metric, not a better model. Write that down; it is the reusable part.

**中文要点**：先对齐"预期"和"度量"是不是同一个量；再排埋点/曝光偏差/流量结构；再分人群拆（聚合涨、新客跌）；再查离线代理指标与线上目标的耦合；最后看反事实与新奇效应衰减。结论常是"离线指标选错了"。
