| Qwen 4 | Qwen2.5 通过 YaRN 加双块注意力（DCA）… | 技术 | 严重 | DCA 讲错两处。①原文「跨块：每个前序块用 keys 的压缩表示」——DCA 压缩的是**相对位置索引**（把前序块的位置映射回训练区间），key 向量一个都没压，K/V 仍是全量。②原文「注意力成本随块数近似线性增长而不是随 token 平方增长」——DCA 不改变复杂度，块间注意力仍是 O(n²)（Qwen2.5-1M 的省算力来自另加的稀疏/top-k 注意力）。题干问「解释其原理」，两处原理都错。应为：DCA 只做位置重映射以复用训练过的相对位置，算力不变。 |
| 跨公司 5 | 解释 FlashAttention。它并没有减少 FLOPs… | 技术 | 中等 | 表里「HBM 流量：FlashAttention = O(N)」不成立。FA 的 HBM 访问量是 Θ(N²d²/M)（M 为 SRAM 容量，FA 论文 Table 1），d=128、M≈50K 元素时约 0.32·N²，**仍是二次**，只是常数小；O(N) 的是**激活显存**，不是 HBM 流量。 |
| 跨公司 15 | 解释 SwiGLU，以及为什么现代 LLM 的 MLP… | 技术 | 中等 | 「8/3 取整到硬件友好倍数，所以 Llama 在 d=4096 时用 14336」因果错。8/3×4096 = 10922.7，取整到 256 的倍数应得 **11008**（Llama-2 7B 正是 11008）；14336 = 3.5×4096 是 Llama-3 主动加宽 FFN，不是取整结果（差 31%）。应为：8/3 是等参数量取值，Llama-3 另有取舍。 |
| DeepSeek 2 | DeepSeek-V3 使用了无辅助损失的负载均衡… | 技术 | 中等 | 公式写成 $s_{i,t}=\text{softmax}(u_t^\top e_i)$，但 V3 用的是 **sigmoid** 亲和度（softmax 是 V2/DeepSeekMoE 的写法）；且 V3 的门控权重需在选中集合内归一化 $g_{i,t}=s_{i,t}/\sum_{j\in\text{TopK}} s_{j,t}$，答案写 $g_{i,t}=s_{i,t}$ 漏了归一化。 |
| 字节 2 | 梳理从 MHA 到 MQA、GQA 和 MLA 的演进… | 技术 | 中等 | MLA 行「压缩到约 `d_c/h·d_h`」量纲不对：512/(64×128)=0.0625 是个无量纲数，不是缓存大小，也不是正确比例。每 token 缓存应为 $d_c+d_h^{R}$，相对 MHA（$2hd_h$）的比例是 $(512+64)/(2\times64\times128)=3.5\%$，答案给的 6.25% 也偏高（漏了 ×2 与解耦 RoPE key）。 |
| 美团 5 | MoE 如何工作…用 Python 实现一个 MoE | 技术 | 中等 | 参考实现两处硬伤：①`self.bias = torch.zeros(n_experts)` 是普通张量，不是 `register_buffer`，x 在 CUDA 上时 `self.gate(x) + self.bias` 直接设备不匹配报错，且不会进 state_dict；②bias 在 softmax **之前**相加（`logits = gate(x) + bias` → `softmax`），使其进入门控权重，与同文档（GLM 3、DeepSeek 2）反复强调的「bias 只参与 top-k 选路、不进 gate 权重」自相矛盾；且 bias 全程没有更新规则，实际不起均衡作用。 |
| 腾讯 1 | 为什么生成式 LLM 采用仅解码器架构… | 技术 | 中等 | 「编码器-解码器要把整段源文本挤过一个固定宽度的交叉注意力接口」不成立：交叉注意力在**每一层**都能访问编码器全部 $n$ 个位置的 $[n,d]$ 表示，不是单个定宽向量，也不存在信息瓶颈。真实差别是多一层编码表示、独立参数与训练信号分配，以及无法直接 attend 原始 token。 |
| 美团 1 | 讲一遍 Transformer…编码器为什么需要 FFN | 技术 | 中等 | 「注意力是 value 的凸组合，后面不接非线性映射，堆多少层仍等价于输入的线性映射」数学上错：softmax 权重依赖输入，纯注意力堆叠是**非线性**映射；已知结论是纯注意力会**秩塌缩**（Dong et al. 2021），不是退化为线性映射。应为：注意力缺的是逐 token 的非线性特征变换与容量，而非「整体是线性的」。 |
| 跨公司 1 | 解释缩放点积注意力…1/sqrt(d_k) | 技术 | 轻微 | 对比表表头「除以 $1/\sqrt{d_k}$」把方向写反：缩放是**乘** $1/\sqrt{d_k}$（等价于除以 $\sqrt{d_k}$）。同表「logit 的 σ = 1」那一行只有按「除以 $\sqrt{d_k}$」才成立，表头与数据自相矛盾。 |
| 跨公司 16 | 请逐个张量地讲一遍 decoder-only 前向… | 技术 | 轻微 | 「参数 ≈ 12Ld²+Vd ≈ 8B」算不平：12×32×4096² + 128256×4096 = 6.44B + 0.53B = **6.97B**。Llama-3-8B 实际 8.03B 需要 GQA（KV 只有 1/4）、3.5d 的 SwiGLU、以及**未共享**的 lm_head（再多 0.53B）；该式对 GQA+SwiGLU 只是近似，不能自称复现 8B。 |
| 滴滴 1 | Transformer 中的 FFN 层是做什么的… | 技术 | 轻微 | 「SwiGLU 用 8/3·d，是为了去掉常数项后参数量持平」原因写错：8/3 来自 SwiGLU 有**三个**矩阵（$3d\,d_{ff}=2d\cdot4d\Rightarrow d_{ff}=8d/3$），与「常数项/偏置项」无关。 |
| 跨公司 3 | 什么是 MQA 和 GQA…它们各自牺牲了什么 | 技术 | 轻微 | 「通常 8 个 KV 头对 32–64 个 query 头，即 8 倍缓存削减」前后不一致：相对 MHA 的倍数 = 每个 KV 组内的 q 头数 = h/g；32/8 只有 **4×**，64/8 才是 8×。同文 Mistral 一节写「32Q/8KV → 小 4 倍」是对的，此处应改成 4–8×。 |
| 跨公司 2 / 淘天 4 | KV cache 公式 / prefill vs decode | 技术 | 轻微 | 同一文档对 PagedAttention 之前的浪费给出两个互斥口径：跨公司 2 说「碎片浪费 20–40%」，淘天 4 说「预留浪费 30–60%」。vLLM 论文（Kwon et al., SOSP'23）的口径是 **60–80%** 的 KV 显存被浪费（只有 20.4–38.2% 存真实 token 状态）。建议统一并注明出处。 |

## 无问题抽样

- **跨公司 2（KV cache 公式）**：$2\times32\times8\times128\times2=131{,}072$ B = 128 KiB/token、32k 单序列 4 GiB、70B（L=80）320 KiB → 10 GiB，四步复算全对。
- **跨公司 8（RoPE / PI / YaRN）**：$\theta_i=\text{base}^{-2i/d}$、PI 的 $m\mapsto m L_{train}/L_{new}$、YaRN 的 NTK-by-parts 与 $\sqrt{1/t}$ 温度、400 步/0.1% 预训练量，均与原文一致。
- **Kimi 2（MLA vs GQA 三档缓存）**：MHA-128 头 64 KB、GQA-8 4 KB、MLA $(512+64)\times2$ B = 1.1 KB 全部复算正确，$4096/1152\approx3.6$ 与「再小 3–4 倍」吻合。
- **字节 2（80 层 70B 级 MHA/GQA 数字）**：$2\times80\times64\times128\times2=2.62$ MB、$2\times80\times8\times128\times2=0.33$ MB，8× 差值与文一致（该题问题只在 MLA 那一行的公式，见上表）。
- **淘天 4（prefill/decode 带宽账）**：$2\times80\times8\times128\times2=327{,}680$ B/token，4k 上下文每生成一 token 重读 $327\text{KB}\times4096=1.34$ GB，算术与结论均正确。
